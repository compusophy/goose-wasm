Goose vs Rust
compiled to bare WebAssembly, racing in your browser

Goose is a new memory-safe systems language with no heap: every dynamic value lives inline on compiler-managed data stacks. It compiles to C, so I wrote a freestanding runtime that lets that C target wasm32-unknown-unknown directly, then built the language's own benchmark suite to WebAssembly twice: the Goose programs, and the Rust versions that ship next to them. Same programs, same inputs, same checksums, same engine. The runtime, harness and every number are on GitHub.

How Goose gets onto wasm

The Goose compiler emits one C file per program. Everything a hot loop touches is inline in that file: pushes, indexing, varints, relative links. What it leaves to a separate runtime object is small and boring: aborts, number formatting, printing, and handing out data stack regions. That split is what makes a bare-wasm port practical. The replacement runtime is under 500 lines of C with no libc behind it, and a Goose module imports at most four functions from its host.

Data stacks are the interesting part. Natively, each one is a large address-space reservation whose pages commit on first touch, followed by an unmapped guard gap. Linear memory has no page protection and grows only at its end, so here each region is a memory.grow of the whole reservation. Engines map those pages lazily, so an untouched reservation costs address space rather than RAM. The guard gap is what wasm cannot provide.

The power-of-two bug

The first full run had one outlier: blur took 99 ms in Goose against 58 ms in Rust, though the two inner loops disassembled to nearly the same instructions: nine byte loads, the same shifts and adds, one store. Timing the phases separately put the whole gap in the kernel, so the cause had to be where the data was, not what the code did.

Each data stack region was exactly as long as its reservation, so the source image and the destination image started exactly 1 GB apart. With a power-of-two distance, pixel x of row y in both images agrees in every address bit below bit 30, which includes every bit the L1 and L2 caches use to pick a set. The rows the kernel reads and the row it writes compete for the same few cache lines.

The fix is cache coloring, four lines in the runtime: start each new region a different multiple of 64 bytes into an extra page. I first took this for 4K aliasing between loads and stores. Isolating the two showed that sharing only the low 16 bits costs 2 to 10 percent here, and the power-of-two distance costs the rest.
